"도달"은 운영에서 그 입력이 Lambda까지 올 수 있는지다. 실제 Function URL과 CloudFront의 변환은 이번에 확인하지 못했다(Phase 2).

**차이가 없던 것:** FE가 보내는 쿼리 형태(`+`·`%20`·`%2B`·`%3D`·`%26`·`%2C`·한글), 쿠키 배열, 로그인·갱신·로그아웃의 `Set-Cookie`, 로그인 한도, 오류 본문의 `code`, CORS 사전 요청, 한글 본문, base64 본문(세 경로 모두, A는 `Vary` 빼고), 내부 작업 6종 분기, 로그의 이메일 가림과 요청 ID 연결. 응답 204를 내는 API는 코드에 없어 해당 항목은 넣지 않았다. 멀티파트·바이너리 응답·스트리밍·리다이렉트를 쓰는 코드도 없다(`src/main/kotlin` 검색).

**비교 전에 정규화한 것:** 응답 시각·토큰·쿠키의 `Expires`, `retry-after` 값, JSON 키 순서, 검증 오류 메시지의 순서(실행마다 달라진다), 쿠키 순서, 전송 계층이 다시 만드는 헤더(`date`·`connection`·`keep-alive`·`transfer-encoding`·`content-length`). 후보 B가 `Content-Type`을 `;charset`이 아니라 `; charset`으로 쓰는 것도 뜻이 같아 정규화했다. ID는 시드 값이 고정이라 정규화하지 않았다.

**Lambda 전용 15개의 기준:** Tomcat에 대응값이 없어 현재 MockMvc를 기준으로 삼았고, 내부 작업은 응답만으로 부족해 DB 값·로그 표식으로 서비스 도달을 확인했다(`l-job-*`).

### 운영 로그에서 찾은 `%ZZ`·`|` 발생 건

조회 전용 키로 Logs Insights를 돌렸다(2026-11-07, `/aws/lambda/link-sphere-api`, 보존 90일 전체).

```
filter @message like /Malformed escape pair|Illegal character in|URISyntaxException/ | stats count() as n
```

스캔 442,379건에서 0건이다. 그래서 최근 90일에는 실제로 맞은 요청이 없다. 입력이 Lambda까지 오는지는 모른다.

### DB가 돌아온 직후의 500은 후보의 결함이 아니다

DB 없이 기동한 뒤 DB가 돌아오면 Tomcat과 후보 A는 첫 요청이 500이고 둘째부터 200이다. MockMvc와 후보 B는 첫 요청부터 200이다. 원인을 따라갔다.

- Tomcat에서 DB가 돌아온 뒤 12초 기다리면 첫 요청이 200이다. 기다리지 않으면 500이다(직접 실행. `run.sh`의 "DB 없이 기동" 순서에서 `docker start serving-db`와 `pg_isready` 뒤에 `sleep 12`를 넣어 재현한다).
- 일반 `java`는 실패한 DNS 조회를 10초 기억한다(이미지의 `java.security:358`, `networkaddress.cache.negative.ttl=10`).
- Lambda Java 런타임은 이 값을 1초로 줄인다(`aws-lambda-java-runtime-interface-client` 2.12.2 `AWSLambda`의 `DEFAULT_NEGATIVE_CACHE_TTL = "1"`, `javap`로 확인).
- 이번 실험에서 DNS 실패가 생긴 이유는 Docker가 멈춘 DB 컨테이너의 이름을 지우기 때문이다(로그의 `UnknownHostException`). Docker가 이름을 지우는 일은 운영에 없다.

그래서 후보 A의 감점 근거로 쓰지 않는다. 다만 후보 A는 일반 `java`로 돌기 때문에, 일시적 DNS 실패를 1초가 아니라 10초 기억한다는 차이는 실제로 남는다.

## 후보별로 새로 생기는 것

**후보 A(Web Adapter + Tomcat).** 표준 Tomcat 그 자체라 입력 처리 차이가 가장 적다(`Vary` 빼면 3건). 대신 값이 여럿인 응답 헤더 손실, 함수 실패가 응답으로 바뀌는 문제, 헤더 한도 저하를 앱 코드로 메워야 한다. `POST /internal/lambda-events`와 스냅샷 훅이 HTTP 경로로 새로 생긴다. 외부 요청은 어댑터가 `x-amzn-request-context`를 덮어써 막히지만(`l-ext-forged` 403, DB 행 유지), 8081 루프백 포트가 다시 열리고 훅 자체는 루프백에서 막지 않는다. 앱 안에서 임의 주소로 요청을 보내는 코드(SSRF)가 뚫리면 닿을 수 있어 새 공격면이다. 내부 경로 3개가 OpenAPI 스펙에 실리고, 함수 실패의 `errorType`이 Java 예외 이름이 아니라 어댑터의 Rust 타입으로 바뀐다. 지금 `LambdaHandler`에 있는 `FunctionUrlOriginGuard` 호출도 PoC에서는 빠져 있어, 옮기면 필터로 다시 만들어야 한다. 스냅샷 훅 순서는 컨테이너 안에서 직접 불러 확인했다(연결 2 → 전 훅 204 → 연결 0 → 후 훅 204 → 200, 200). 실제 스냅샷 동작은 모른다.

**후보 B(serverless-java-container).** 내부 작업 분기·Java 런타임·소켓 없음이 그대로다. SnapStart 처리도 그대로일 것으로 보지만 RIE에는 SnapStart가 없어 확인하지 못했다. 필터가 모두 돌고 `spring-test`가 운영에서 빠진다. 남는 차이는 `q-eq`, `p-slash`, 깨진 입력의 처리다. 라이브러리 안의 동작이라 고치려면 이벤트를 넘기기 전에 우리가 바꿔야 한다(확인 안 함). 라이브러리가 요청마다 접속 로그 1줄(IP 포함)을 INFO로 남긴다. `setLogFormatter(null)`이면 끌 수 있다(`LambdaContainerHandler.java:188,219`, 소스를 읽음, 실행 안 함). 2.x가 Boot 3.x 라인이고 3.x가 Boot 4.x 라인이다([저장소 README](https://github.com/aws/serverless-java-container)). 2026-10-28에 2.1.7, 2026-10-27에 3.0.5가 나왔다.

## 이번에 알 수 없는 것

- **콜드 스타트:** RIE에는 SnapStart가 없다. "Tomcat이면 빨라진다"도 "B면 같다"도 근거가 아직 없다.
- **실제 Function URL·CloudFront 변환:** 이벤트는 AWS 문서 형식으로 만들었다. `%ZZ`·`|`·`%2F`가 실제로 어떻게 넘어오는지는 모른다.
- **복원 뒤 연속 호출:** 2026-07-25 어댑터 장애가 "첫 요청만 성공"이었다. 후보 A는 실제 복원에서 봐야 한다.

참고 값(결론에 쓰지 않음): `Started … in`은 전체 실행을 통틀어 네 대상 모두 약 7~10초였고 실행마다 순서가 바뀌었다. JAR 크기 차이는 약 1.3%다.

다음 단계는 이 결과를 본 뒤 정한다. 운영 구조는 바꾸지 않았다.
